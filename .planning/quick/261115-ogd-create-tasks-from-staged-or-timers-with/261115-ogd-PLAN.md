# Create TaskNotes tasks from either pane

Add a `Create new task` route to the existing Staged and Timers task-picking flows. It must open TaskNotes' registered `tasknotes:create-new-task` command, then route the one task saved by that dialog back to the pane that initiated it: stage it at the selected Staged insertion point, or persist it as an idle Timers card. Creation must never start time tracking. Do not modify TaskNotes itself, add or run tests, publish a release, or disturb unrelated working-tree changes (especially the existing `styles.css` wikilink fix and planning/config files).

1. **Add a safe, plugin-wide creation capture.** In `src/tasknotes/runtime-api.types.ts` and `src/tasknotes/TaskNotesBridge.ts`, add the documented `task.created` event and the minimal typed payload needed to obtain the created `TaskInfo`, while keeping all Runtime API access inside the bridge. Add `src/state/TaskCreationCoordinator.ts` as the single owner of an in-flight request across every pane leaf. It must verify that TaskNotes is ready, `tasks.events` remains available, and `tasknotes:create-new-task` is registered; subscribe/capture before executing the command; accept only the matching next `task.created`; clear the request before dispatching it; and cancel cleanly if command execution fails, the newly opened Obsidian modal closes without a save, TaskNotes disconnects, a newer request supersedes it, or the plugin unloads. Use a request token and detachable listeners/observer so cancellation cannot leak a handler or let a later unrelated task be captured. Expose availability/busy reasons for UI gating, and do not call `tasks.create` or TaskNotes internals.

2. **Route the saved task to the originating flow.** In `src/main.ts`, instantiate and dispose one coordinator beside the bridge/controllers and pass it to every `TimerPaneView`. In `src/ui/TimerPaneView.ts` and `src/ui/TaskPickerModal.ts`, expose a clearly labelled `Create new task` action from both the Staged picker (preserving its `beforePath` insertion target) and the Timers Add-task picker. Close the picker before opening TaskNotes' dialog, disable the action with a useful reason whenever the destination, coordinator, command, or TaskNotes capability is unavailable, and reflect the coordinator's global busy state in all open pane leaves. On success, call exactly one existing destination method: `StagingController.stage({ taskPath, title, beforePath })` for Staged, or `IdleCardStore.add(task)` for Timers. Surface blocked/failed destination outcomes through the existing notification/log patterns; do not invoke `TimerController.start`, `IdleCardStore.start`, or any time-write API.

3. **Verify without tests and preserve unrelated work.** Review `git diff -- src/tasknotes/runtime-api.types.ts src/tasknotes/TaskNotesBridge.ts src/state/TaskCreationCoordinator.ts src/main.ts src/ui/TimerPaneView.ts src/ui/TaskPickerModal.ts` to confirm the change stays within the planned source files and that no TaskNotes clone, `styles.css`, planning state/config, or unrelated dirty file was altered. Run `npm run typecheck` and `npm run lint` only; do not add, update, or execute tests. Confirm from the resulting code paths that modal cancellation leaves no pending capture, concurrent pane requests cannot both claim a task, Staged creation preserves insertion position, Timers creation persists an idle card, and neither route starts a timer.
